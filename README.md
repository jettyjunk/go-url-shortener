# Go URL Shortener

Сервис сокращения ссылок, написанный на Go. Принимает длинный URL, генерирует уникальный короткий код и перенаправляет пользователя на исходный адрес.

Pet-проект для изучения Go Backend Development: слоистой архитектуры, работы с PostgreSQL и Redis, проектирования HTTP API, обработки ошибок и тестирования бизнес-логики.

## Возможности

- Создание коротких ссылок через HTTP API.
- Перенаправление на исходный URL по короткому коду.
- Кеширование оригинальных URL с помощью Redis.
- Автоматическое сохранение данных в Redis при Cache Miss.
- Валидация URL: поддерживаются только протоколы HTTP и HTTPS.
- Генерация случайных непредсказуемых коротких кодов.
- Обработка коллизий при генерации кодов.
- Хранение ссылок в PostgreSQL.
- Управление схемой базы данных через миграции.
- Передача контекста и обработка таймаутов.
- Запуск инфраструктуры через Docker Compose.

## Быстрый старт

### Требования

- Go (версия, указанная в go.mod)
- Docker и Docker Compose
- CLI golang-migrate

Установка CLI для миграций:

```bash
go install -tags 'postgres' github.com/golang-migrate/migrate/v4/cmd/migrate@latest
```

### Запуск проекта

1. Клонирование репозитория:

```bash
git clone https://github.com/jettyjunk/go-url-shortener.git
cd go-url-shortener
```

2. Создание файла конфигурации:

```bash
cp .env.example .env
```

3. Запуск PostgreSQL и Redis:

```bash
make up
```

4. Применение миграций:

```bash
make migrate-up
```

5. Запуск приложения:

```bash
make run
```

По умолчанию HTTP-сервер слушает порт `5050`.

## API

### Создание короткой ссылки

`POST /shorten`

Принимает исходный URL и возвращает короткую ссылку.

**Пример запроса:**

```bash
curl -i -X POST http://localhost:5050/shorten \
  -H "Content-Type: application/json" \
  -d '{"url":"https://example.com"}'
```

**Ответ — 201 Created:**

```json
{
  "short_url": "http://localhost:5050/aB3xK9q"
}
```

| HTTP-статус | Описание |
|---|---|
| `201 Created` | Ссылка успешно создана |
| `400 Bad Request` | Некорректный JSON или URL |
| `500 Internal Server Error` | Внутренняя ошибка сервера |

### Переход по короткой ссылке

`GET /{code}`

Перенаправляет пользователя на исходный URL.

**Пример запроса:**

```bash
curl -i http://localhost:5050/aB3xK9q
```

| HTTP-статус | Описание |
|---|---|
| `302 Found` | Перенаправление на исходный URL |
| `404 Not Found` | Короткая ссылка не найдена |
| `500 Internal Server Error` | Внутренняя ошибка сервера |

### Разделение ответственности

- **Handler** — принимает HTTP-запросы, разбирает входные данные и формирует HTTP-ответы.
- **Service** — содержит бизнес-логику, валидацию URL, генерацию коротких кодов и обработку коллизий.
- **Repository** — отвечает за хранение и получение ссылок в PostgreSQL.
- **CachedLinks** — оборачивает реализацию хранилища и добавляет Redis-кеширование.
- **Codegen** — отвечает за генерацию случайных коротких кодов.

Интерфейсы определяются на стороне потребителей. Это позволяет тестировать бизнес-логику независимо от конкретных реализаций хранилищ.

## Кеширование с Redis

Для кеширования используется паттерн **Cache-Aside** (ленивое кеширование).

При запросе оригинального URL по короткому коду приложение сначала обращается к Redis.

**Алгоритм работы:**

1. Проверяется наличие URL в Redis по ключу `link:{code}`.
2. Если запись найдена (Cache Hit), URL возвращается непосредственно из кеша.
3. Если запись отсутствует (Cache Miss), выполняется запрос к PostgreSQL.
4. Полученный URL сохраняется в Redis с установленным временем жизни (TTL).
5. Последующие запросы могут обслуживаться непосредственно из кеша.

**Особенности реализации:**

- Redis используется только для ускорения чтения данных.
- Создание ссылок выполняется через PostgreSQL.
- Записи в Redis создаются при первом успешном получении ссылки.
- При ошибках чтения или записи Redis приложение логирует проблему и продолжает работу через PostgreSQL.

Таким образом, Redis выступает дополнительным слоем кеширования, а PostgreSQL остаётся основным источником данных.

## Технические решения

### Генерация коротких кодов

Для генерации используются 7 случайных символов из алфавита `0-9a-zA-Z`.

Генерация выполняется с помощью `crypto/rand`, что обеспечивает непредсказуемость кодов.

Пространство возможных комбинаций составляет около 3,5 триллиона вариантов.

### Обработка коллизий

Для поля `code` в PostgreSQL установлено ограничение уникальности.

При возникновении конфликта PostgreSQL возвращает ошибку `23505`. Репозиторий преобразует её в собственную ошибку `ErrCodeExists`.

После этого сервис генерирует новый код и повторяет операцию. Максимальное количество попыток — 5.

### HTTP-редирект

Для перенаправления используется статус `302 Found`.

В отличие от `301 Moved Permanently`, временный редирект позволяет не закреплять адрес назначения в браузере на постоянной основе и сохранять возможность обработки последующих переходов приложением.

### Валидация URL

При создании короткой ссылки проверяются:
- Корректность URL.
- Наличие хоста.
- Допустимая схема: `http` или `https`.

Это предотвращает создание ссылок с неподдерживаемыми протоколами.

### Контекст и таймауты

Контекст HTTP-запроса передаётся между слоями приложения до уровня работы с базой данных.

Для запросов к PostgreSQL предусмотрен таймаут 5 секунд.

### Обработка ошибок

Каждый слой возвращает ошибки вышестоящему компоненту, используя обёртку `%w`.

Репозиторий предоставляет собственные ошибки, не раскрывая детали реализации PostgreSQL.

Ошибки Redis логируются, но не прерывают обработку запроса, если данные можно получить из PostgreSQL.

Клиенту при внутренней ошибке возвращается общее сообщение без раскрытия технических деталей.
